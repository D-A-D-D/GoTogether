- **[open]** — Refresh-token rotation vs. a lost response — the refresh token rotates on every use, so if a refresh request reaches the server but its response never reaches the browser (tab closed or navigated mid-request, flaky mobile network), the cookie keeps a token the server already revoked and the next refresh 401s: the user is logged out for no fault of their own. One lost session was observed in production-mode testing after navigating away mid-refresh — probable cause, unproven. Options: a short grace window where a just-rotated token still works (tracked as ROADMAP Open decision #7, since it's a security-policy tradeoff), or leave strict and accept occasional re-logins. `RefreshToken.replacedBy` already records the rotation chain, so a grace check wouldn't need a schema change. *2026-10-17*

- **[resolved 2026-10-23]** — Trust can be farmed without a real trip — found while testing reviews: trip creation accepts dates in the past (`CreateTripDto` only checks `endDate ≥ startDate`), and `Trip.complete()` only checks that the end date has passed. So someone can create a trip that has already "ended", approve a couple of friends, mark it complete in a click, and exchange five-star reviews for a trust-score gain — no actual trip involved. The ±15-per-trip cap and the reviewer-weight formula blunt it but don't stop it, since nothing limits how many such trips one person makes. Cheap hardening: reject a `startDate` in the past at creation (also stops past-dated trips appearing as OPEN in discovery), and require at least two approved members before a trip can be completed. Feeds directly into the Phase 3 collusion-detection item, which would otherwise be chasing a loophole that's easy to close up front. **Done 2026-10-23** exactly as proposed, plus one extension: completion now also waits for the trip's *last day* to be over (not just its start), since otherwise a trip created for today could be completed immediately. See ROADMAP.md. Still open by design: friends running many real trips together — Phase 3's collusion detection. *2026-10-23*

- **[open]** — Paging follow-ups — leftovers from adding paging. (a) *Discovery cost*: every page re-fetches and re-scores *all* candidate trips and slices the result, so N pages cost N full scorings. Fine now; BLUEPRINT §10's "precomputed match scores, cached per user" is the real answer once volume grows, and a cursor (score, start, id) would then replace `offset`. (b) *"Is there more?" is inferred* from a full page coming back, so a total that is an exact multiple of the page size costs one extra, empty request before the button disappears; the API could return a `hasMore` flag. (c) *Chat has no "new messages ↓" cue*: if you're reading history and messages arrive you're (rightly) not scrolled, but nothing says they're there — a small "New messages" pill that jumps to the latest is the usual fix. (d) There's no search within chat history — once a conversation is long, finding "where did we say we'd meet?" means scrolling back page by page. *2026-10-24*
- **[resolved 2026-10-23]** — Push subscription follows the device, not the account — gaps found building the subscribe UI. (a) *User switching without logging out*: logout removes this device's subscription, but logging in as a different user while the old session is still valid (e.g. submitting the login form while already signed in) doesn't, so the new user could receive the old user's notifications. Fix: record which user owns the device's subscription (localStorage), and at login drop the browser subscription if the owner differs. (b) *Re-enabling after logout*: because logout removes the subscription, someone logging back in on their own phone has to switch notifications on again; remembering per-device opt-in (the same owner record) would let it re-subscribe silently when permission is still granted. (c) *The "on" state is read from the browser only* — if the server dropped the subscription (a 410 cleanup) the page still says on while nothing arrives; re-saving the existing subscription when the profile page loads would heal that. **Done 2026-10-23, all three** — the device records which account opted in; a different account logging in has the subscription dropped; the owner gets it restored quietly and re-saved daily. - **[scheduled → foundation done 2026-10-24; the rest open — needs your decisions]** — Moderation: the console, suspension enforcement and audit trail are built (see ROADMAP.md), with these choices made **by default, not by you** — override any: **who reviews** = an `ADMIN` role on `User`, granted only by an operator script; **what suspension blocks** = login (403 with a clear message), every authenticated API call (401), and chat (connect, send, live delivery), with refresh tokens revoked; **no softer state** and **no appeal** yet. - **[open]** — Moderation follow-ups — gaps left by the foundation. (a) *A restricted host's trip itself*: hiding it from discovery and refusing new joins is done (2026-10-25), but the trip stays alive for its current members with nobody able to approve, edit, complete or cancel it — so it can never be completed or reviewed. Probably wants a moderator action (cancel the trip, or hand it to a member) rather than an automatic one; also decide what a ban does. Related: restricted *members* stay on the roster, in expenses and in the capacity count; the host can remove them, but nothing prompts it. (b) *Cache across instances*: account state is cached per process for 30 seconds, so with more than one API instance a suspension (or a role change) takes up to 30s to reach the others — a shared invalidation (Redis pub/sub, which Phase 4's chat adapter would bring anyway) or a shorter TTL. (c) *The suspended person isn't told until they next log in*: a mid-session suspension looks like being signed out; the 401 path could carry the reason. (d) *No way to act without a report*: suspend/ban are only on report cards, though the API takes any user id; and no per-user history view — the audit rows exist, the console shows only each restricted account's latest decision. (e) *No one is told*: neither the reporter (see Reporting follow-ups) nor the reported person is notified of an outcome. (f) *Admin accountability*: no second approver for bans, and no listing of admins or role changes (the operator script prints but doesn't record). (g) *The report queue isn't paged or searchable*; fine at launch volume, not past it. *2026-10-24*
