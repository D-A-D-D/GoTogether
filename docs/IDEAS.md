- **[resolved 2026-10-17]** — Stale service worker breaking live verification — the real cause was the worker's design (cache-first on every GET, including cross-origin API reads), not a test-hygiene problem. The worker is now narrow and production-only, and dev unregisters leftovers itself, so "clear SW registrations before testing" is no longer a required step. *2026-09-30*
- **[open]** — Refresh-token rotation vs. a lost response — the refresh token rotates on every use, so if a refresh request reaches the server but its response never reaches the browser (tab closed or navigated mid-request, flaky mobile network), the cookie keeps a token the server already revoked and the next refresh 401s: the user is logged out for no fault of their own. One lost session was observed in production-mode testing after navigating away mid-refresh — probable cause, unproven. Options: a short grace window where a just-rotated token still works (tracked as ROADMAP Open decision #7, since it's a security-policy tradeoff), or leave strict and accept occasional re-logins. `RefreshToken.replacedBy` already records the rotation chain, so a grace check wouldn't need a schema change. *2026-10-17*
- **[open]** — Cross-tab refresh coordination — `refreshSession` is now single-flight *per tab*, but two tabs of the same browser share one refresh cookie and each runs its own refresh, so they can still race each other. `navigator.locks` (or a `BroadcastChannel`) would make it single-flight across tabs. Matters mostly for people who keep several tabs open. *2026-10-17*
- **[open]** — Make logout survive navigation — `POST /auth/logout` is cancelled (`ERR_ABORTED`) if the page navigates before it completes, leaving the server-side refresh token live and the user silently still signed in (seen when a hard navigation followed a click). `fetch(..., { keepalive: true })` on the logout call is the usual cheap fix. Low risk in normal use (the app navigates client-side after logout) but wrong for a "log out" button on a shared device. *2026-10-17*
- **[open]** — Push notifications for expenses — the four push triggers wired so far (join request, approval, chat message, resolved review) don't include money. Someone logging an expense that involves you, or marking your share paid, is exactly the kind of thing people want to hear about without opening the app. Easy to add to `ExpensesService` through the existing `NotificationsService`; blocked on the same missing subscribe UI as the rest of push. *2026-10-17*
- **[open]** — Show who's on a trip — the trip detail page only shows "Members 2/3". `GET /trips/:id/members` (added for the expenses form) already returns names, roles and trust scores for approved members, so a members list on the trip page is nearly free. Currently invisible to a prospective joiner by design (the endpoint is members-only); deciding what a *non-member* may see of the group (names? just trust scores? nothing?) is a privacy call worth making deliberately. *2026-10-17*
- **[open]** — Dev ergonomics on Windows — `nest build` fails with EPERM while the API dev server is running, because the loaded Prisma query-engine DLL can't be unlinked from `dist/`. Typecheck with `tsc --noEmit -p tsconfig.build.json` while the server is up, or stop it first. A separate build `outDir` for local verification would remove the collision. Not an issue in CI. *2026-10-17*
- **[open]** — API latency — through this verification pass, ordinary GETs (trip detail, discover, chat history, a profile save) routinely took 3–8 seconds in local dev against the hosted Neon database, not just on the first request after idle. Not diagnosed: could be Neon region distance multiplied by several sequential Prisma round trips per request, or compute wake-ups. Worth measuring (per-request query count and time) before the UI feels slow to real users; candidates are co-locating the API with the database region, fewer sequential queries in hot paths, and caching the static `/tags` response. *2026-10-17*
