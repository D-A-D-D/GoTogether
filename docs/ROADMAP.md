- **2026-09-28** — Expense splitting (`apps/api/src/expenses/`): new `Expense`/`ExpenseSplit` models (a ledger, not a payment rail — BLUEPRINT §06). `POST /trips/:id/expenses` supports equal-split (default: all approved members) and custom per-person splits (validated to sum exactly to the total); `GET /trips/:id/expenses` for history; `GET /trips/:id/balances` returns **pairwise** net balances from the caller's perspective (not a minimized settlement graph — every number traces to a real unsettled split row, which matters more for a financial feature); `PATCH .../splits/:splitId/settle` is the manual "mark as paid," settable by either the debtor or the payer. **Fully smoke-tested against the real database**: non-member blocked from every endpoint (403); `paidById` validated as an approved member; custom-split sum mismatch and duplicate-userId both rejected (400); a two-expense scenario (host paid 300 split 3 ways, member B paid 150 split 3 ways) produced the exact expected net balances (B owes host net 50, C owes host 100); an uninvolved third member blocked from settling a split they're not party to (403); settling correctly recomputes the payer's balance; double-settle rejected (409).
- **2026-09-28** — Review window & trust-score engine (`apps/api/src/reviews/`): `Trip.complete()` gate (host-only, only after `endDate`); `Review` model, one row per (trip, reviewer, reviewee); `POST /trips/:id/reviews`, `GET .../pending`, `GET .../received`, `GET /users/me/trust-events`. Blind window (BLUEPRINT §05) resolves a pair the moment BOTH have reviewed each other (mutual trigger) or after 14 days via a **lazy sweep** run opportunistically on the next relevant request — no scheduled-job infra exists yet, logged as a Phase 3/4 follow-up. Score update is ELO-inspired: `delta = K × reviewerWeight × durationWeight × (rating − expected)`, `expected` = the reviewee's own current score (so a rating that merely confirms it barely moves the needle; one that contradicts it moves it more), `K` shrinks from 6 to 3 after a reviewee's first 5 completed trips, `reviewerWeight` = the reviewer's own trust/100 (the anti-gaming lever), capped at ±15 total per trip via an order-independent incremental clamp. **Fully smoke-tested against the real database, including the trickiest parts**: completion gate (host-only, pre-endDate blocked), review validation (self/non-member/duplicate/pre-completion all blocked), the blind window confirmed to hide an unmatched review from both `listReceived` and the counterpart's dashboard until the mutual trigger fires (verified 50→52 for both sides, matching the formula's hand-computed value exactly); **anti-gaming confirmed twice** — a trust-10 reviewer's perfect review of another user produced a delta of 0 (rounds away under the tiny reviewerWeight), and the same effect independently showed up on a harsh 1-star review from a similarly low-trust reviewer; the **±15 per-trip cap confirmed** to fully suppress a further review's delta to 0 once a trip's cumulative movement hit the ceiling; the **14-day timeout sweep confirmed** to process a backdated, un-reciprocated review on the next fetch.
- **2026-09-28** — Push notifications (`apps/api/src/notifications/`): VAPID-based Web Push (the `web-push` package), `PushSubscription` model (one row per browser/device). `GET /notifications/vapid-public-key` (public — it's not secret, browsers need it to subscribe), `POST`/`DELETE /notifications/subscribe`. Wired as a best-effort side effect into the four moments that actually warrant one: a new join request (→ notifies the host), a request approved or rejected (→ notifies the requester), a chat message sent (→ notifies the other approved members), and a review resolving past the blind window (→ notifies the reviewee — this one can't leak early since it only fires from inside the same code path the blind window already gates). A failed or missing subscription never breaks the action that triggered it. **Backend fully verified against the real database and a real (if fabricated) push pipeline**: subscribe/unsubscribe require auth and round-trip correctly; every trigger point confirmed to actually call `notifyUser`/`notifyUsers` (observed in logs), and the calling action (approve, join, send) always still succeeds even when the push fails; escalated the test subscription through three stages of realism — a malformed key (rejected at length-validation), a random-but-correctly-sized key (rejected at curve-validation), and a genuine P-256 EC key pair (passed *all* cryptographic validation and reached an actual HTTP attempt, failing only on DNS resolution of the fabricated endpoint). **What's unverified**: actual delivery to a real browser — that needs a genuine browser-issued `PushSubscription` (a live web client with a subscribe UI, which doesn't exist yet) or manual testing outside this environment; there's still no subscribe UI to generate a real subscription (the Phase 0 service-worker registration concern was later resolved). Also fixed in passing: CI's dummy-env block was missing `VAPID_*`, which would have crashed the e2e test's app bootstrap on the next push — added a CI-only key pair (separate from the dev `.env` pair) and confirmed the fix by running the e2e suite with `.env` entirely absent.

- **2026-09-30** — Chat UI (`apps/web/src/app/trips/[id]/chat/`): a Socket.io client (`socket.io-client`, `transports: ['websocket']` — skips the HTTP long-polling handshake entirely, both a reasonable production default and, as it turned out, the thing that let this feature be verified live at all) joins the trip's room and listens for `message`; sending emits `sendMessage` with an ack callback for inline error display; history loads via the existing REST endpoint. Logged in docs/IDEAS.md as worth re-confirming with two staggered (not simultaneous) sessions, or in a real browser. Also hit the stale-service-worker-cache issue again here (root-caused and properly fixed 2026-10-17 — see below).
- **2026-10-17** — Service-worker root-cause fix, live re-verification of every GET-driven page, and a refresh-race fix. **Corrects three earlier entries above.** The "Browser pane can't make cross-origin GETs" finding was wrong: the app's own `public/sw.js` was intercepting them. The first worker cache-first'd *every* GET, and its `/api` exemption never matched because the API lives on a different origin (`localhost:3001`, paths like `/users/me`), so API reads were being served from cache or failing — in production that would have shown users stale data indefinitely. The earlier "ruled out the service worker" test was flawed: it unregistered the worker but the already-open page stayed controlled by it. Properly retested with nothing controlling the page, bare cross-origin GETs return 200. **Fix**: `sw.js` (cache `v3`) now ignores everything cross-origin, caches only content-hashed `/_next/static/` and `/icons/` (cache-first), and handles page navigations network-first with the cached shell as the offline fallback; registration is **production-only**, and in dev `register-service-worker.tsx` unregisters any leftover worker and deletes its caches (confirmed to self-heal a worker left over from a production run). **Verified under a production build** (new `web-prod` entry in `.claude/launch.json`): the worker activates and controls the page, its cache holds only same-origin shell assets (no API entries), and cross-origin API GETs succeed while it is in control. **Re-verified live in the browser, with real data, for the first time**: `/profile` (load + tag change saved, `PATCH /users/me → 200`), `/trips/discover` (card with a 90% match), `/trips/mine`, `/trips/[id]` as host (private excluded tags and pending-request list visible) and as member (neither visible), the full request → "pending" → host Approve → members 2/3 loop, chat history, and **two-way multi-user live chat** (host in the browser; the member as an independent Socket.io client, since two browser tabs share one cookie jar and would collide on the rotating refresh token — which likely explains the earlier "stuck second tab" rather than resource contention). **A real bug found and fixed along the way**: `refreshSession()` had no in-flight dedupe, so every dev page load fired two refreshes (React Strict Mode double-runs the mount effect), and any page firing parallel requests with an expired access token would fire several at once; because the refresh token rotates on use, the loser can get a 401, which `apiFetch` treats as "session over" — a spurious logout of a good session, intermittent depending on DB timing. `refreshSession` is now single-flight; confirmed 2 → 1 refresh calls per load with the session still restoring. **Still open, logged not fixed** (see Open decisions #7 and IDEAS.md): a refresh whose response never reaches the browser (tab closed or navigated mid-request) leaves the cookie holding an already-rotated token; one lost session was observed in production-mode testing after navigating away mid-refresh, probable cause but unproven.
- **2026-10-17** — Expenses UI, plus `GET /trips/:id/members`. The new endpoint exists because nothing could list a trip's people: approved members only, visible only to other approved members, exposing just id/name/trust score/role. Page `/trips/[id]/expenses`: your pairwise balances (total owed to you / you owe, per person); an add-expense form (description, whole-number amount, who paid, optional category, split equally across the selected members or set exact per-person amounts — the equal-split preview mirrors the server's remainder rule, so the numbers shown are the numbers stored, and the submit button stays disabled with an inline hint until the shares are valid, e.g. "40 still to assign — shares need to add up to 200"); and a newest-first history with a "Mark paid" button per split for either side of a debt. An "Expenses" link sits beside "Open chat" on the trip page for the host and approved members (`canChat` renamed `isApprovedMember`, since it now gates more than chat). Added a shared `Select` to `form-controls`. **Verified live end to end with real data**: 301 split two ways previewed as 151/150 and was stored that way; a second expense paid by the *other* member with a custom 50/150 split netted against the first (150 − 50 = 100) and read correctly from both sides ("Priya Member owes you 100" / "You owe Aarav Host 100"); settling as the payer (45 → balance 145 → 100) and as the debtor (150 → balance flipped to "Aarav Host owes you 50"); invalid custom splits blocked with the hint; a non-member opening the URL gets a clean "Only approved members…" message rather than a crash or spinner. The members endpoint was separately smoke-tested across roles (both members see host-first `[HOST, MEMBER]`; outsider 403; unauthenticated 401). **One bug found by watching it**: the category field stayed filled after submitting and would have silently labelled the next expense — now cleared along with the description and amount (paid-by and who's included deliberately carry over, since batches of expenses are usually the same group). Web lint, typecheck and production build pass; API lint, typecheck and unit tests pass. `nest build` itself could not run locally while the API dev server was up — Windows won't let it unlink the loaded Prisma query-engine DLL (EPERM), an environment collision, not a code error; CI builds in a clean checkout.
