- **2026-09-28** — Review window & trust-score engine (`apps/api/src/reviews/`): `Trip.complete()` gate (host-only, only after `endDate` — tightened 2026-10-23 to after the last day is over, and with at least two approved members; see below); `Review` model, one row per (trip, reviewer, reviewee); `POST /trips/:id/reviews`, `GET .../pending`, `GET .../received`, `GET /users/me/trust-events`. Blind window (BLUEPRINT §05) resolves a pair the moment BOTH have reviewed each other (mutual trigger) or after 14 days via a **lazy sweep** run opportunistically on the next relevant request — no scheduled-job infra exists yet, logged as a Phase 3/4 follow-up. Score update is ELO-inspired: `delta = K × reviewerWeight × durationWeight × (rating − expected)`, `expected` = the reviewee's own current score (so a rating that merely confirms it barely moves the needle; one that contradicts it moves it more), `K` shrinks from 6 to 3 after a reviewee's first 5 completed trips, `reviewerWeight` = the reviewer's own trust/100 (the anti-gaming lever), capped at ±15 total per trip via an order-independent incremental clamp. **Fully smoke-tested against the real database, including the trickiest parts**: completion gate (host-only, pre-endDate blocked), review validation (self/non-member/duplicate/pre-completion all blocked), the blind window confirmed to hide an unmatched review from both `listReceived` and the counterpart's dashboard until the mutual trigger fires (verified 50→52 for both sides, matching the formula's hand-computed value exactly); **anti-gaming confirmed twice** — a trust-10 reviewer's perfect review of another user produced a delta of 0 (rounds away under the tiny reviewerWeight), and the same effect independently showed up on a harsh 1-star review from a similarly low-trust reviewer; the **±15 per-trip cap confirmed** to fully suppress a further review's delta to 0 once a trip's cumulative movement hit the ceiling; the **14-day timeout sweep confirmed** to process a backdated, un-reciprocated review on the next fetch.

- **2026-10-17** — Service-worker root-cause fix, live re-verification of every GET-driven page, and a refresh-race fix. **Corrects three earlier entries above.** The "Browser pane can't make cross-origin GETs" finding was wrong: the app's own `public/sw.js` was intercepting them. The first worker cache-first'd *every* GET, and its `/api` exemption never matched because the API lives on a different origin (`localhost:3001`, paths like `/users/me`), so API reads were being served from cache or failing — in production that would have shown users stale data indefinitely. registration is **production-only**, and in dev `register-service-worker.tsx` unregisters any leftover worker and deletes its caches (confirmed to self-heal a worker left over from a production run). **Verified under a production build** (new `web-prod` entry in `.claude/launch.json`): the worker activates and controls the page, its cache holds only same-origin shell assets (no API entries), and cross-origin API GETs succeed while it is in control. **Re-verified live in the browser, with real data, for the first time**: `/profile` (load + tag change saved, `PATCH /users/me → 200`), `/trips/discover` (card with a 90% match), `/trips/mine`, `/trips/[id]` as host (private excluded tags and pending-request list visible) and as member (neither visible), the full request → "pending" → host Approve → members 2/3 loop, chat history, and **two-way multi-user live chat** (host in the browser; confirmed 2 → 1 refresh calls per load with the session still restoring. **Still open, logged not fixed** (see Open decisions #7 and IDEAS.md): a refresh whose response never reaches the browser (tab closed or navigated mid-request) leaves the cookie holding an already-rotated token; - **2026-10-23** — Past-date hardening, closing the "trust without a trip" loophole found while testing reviews. Three rules, in one new pure module (`apps/api/src/trips/trip-rules.ts`): (1) a trip can't start in the past — `create()` returns 400, today is fine; (2) `complete()` now requires the trip's *last day to be over* — `endDate` is inclusive ("Dec 1 – Dec 10" includes the 10th), and the old check (`now ≥ endDate` at midnight) let a host complete a trip on its own final day, which would have made rule 1 trivial to sidestep by creating a trip for today and completing it at once; (3) `complete()` requires at least two approved members, so there's someone to review. Dates are UTC — exact for the launch market (India is ahead of UTC), a few hours of lag for anyone west of it, noted in the module. The trip page mirrors the rules in what it *offers* (end-of-day rather than start-of-day, plus a hint when no one else has joined); the server stays authoritative. **Tests — the repo's first real unit tests**: 23 across the pure rules (UTC-day boundaries, the last millisecond of a day, an end date carrying a time of day) and `TripsService.create`/`complete` with a mocked database (a past start is rejected before touching the database, today is allowed, the date is checked before the headcount, only APPROVED members count). - **2026-10-24** — Safety basics: blocking and reporting. A real gap: the `Block` and `Report` tables existed and discovery already honoured blocks, but nothing let a user create either. **Block** (`POST`/`DELETE /users/:id/block`, `GET /users/me/blocks`) follows BLUEPRINT §08 — *symmetric and total*: it doesn't matter who blocked whom. Enforced in **discovery**; **joining and viewing** each other's trips (an identical 404 to a trip that doesn't exist, so a block can't be detected, not even from the "not open" message); the **travellers list**; **chat history** (including messages sent *before* the block); **live chat**, per recipient — the gateway used to emit once to the whole room, and now fetches the room's sockets and skips anyone blocked with the sender, while the sender still gets their own message back so nothing visibly fails; and chat **push notifications**. **Manual delivery check** (the one thing left on push; about five minutes, in a normal Chrome/Edge/Firefox — `localhost` counts as a secure context). Push needs the production build, because the service worker is off in development:
1. `npm run build --workspace apps/web`, then `npm run start --workspace apps/web` (http://localhost:3000), and `npm run dev:api` in another terminal (the VAPID keys are already in `apps/api/.env`).
2. Register or log in as user A and host a trip. Open Profile → **Turn on notifications** → Allow. You should get an immediate "Notifications are on" notification.
3. In a *private window* (its own cookie jar), log in as user B and request to join A's trip.
4. A should receive a "wants to join" notification — try it with A's tab in the background — and clicking it should open the trip page. Also try the chat: B sends a message in an approved trip and A should be notified.
5. In A's window, log out, then have B trigger another event: A should get **nothing** (logout removed the device's subscription). Then log A back in: notifications should resume **without** pressing "Turn on" again (the device remembers A opted in). Finally, log in as a *different* account on that browser: it should show "Turn on notifications" (off) and receive nothing meant for A.
If step 4 never fires, the API log shows why (`Push send failed for subscription …`) — and that is the first real information about the push path.
